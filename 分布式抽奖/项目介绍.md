#  抽奖项目

## 介绍

需求背景：用于对用户的拉新、促活、留存、转化。

主要功能：用户抽奖、签到、积分兑换奖品

技术架构：前后端分离 + 微服务分布式架构 + SpringBoot项目

1. nginx负责反向代理，负载均衡
2. zookeeper负责数据同步
3. redis用于缓解数据库压力
4. MySQL用于保障数据的一致性
5. xxl-job负责定时任务发现事件
6. rabbitmq用于解耦事件发送和事件消费
7. 服务部署在docker上

包含什么模块：主要讲解抽奖功能，主要三个模块 抽奖活动、抽奖策略、奖品发放。扩展了两个模块行为返利模块、消息任务。

（模块如何开发：用户通过决策命令，使用领域对象，通过业务逻辑，产生多个领域事件，过程中调用了一次外部接口）





## 功能流程

### 接口请求处理全流程

1. JWT生成的token校验
2. 限流、降级自己实现的，限流是基于SpringAOP，降级是基于zookeeper
3. 参与活动模块：抽奖次数扣减 + 生成参与活动订单
4. 执行抽奖流程模块：生成奖品订单
5. 奖品发放模块：是由事件驱动的，定时任务发现事件，mq发送，监听器消费。



### 参与活动模块

情景：用户参与抽奖活动时，原流程会直接扣减活动次数

任务：目标是解决查账难、重复消费、异步解耦的问题

行动：扣减用户活动次数后，生成抽奖订单。



### 执行抽奖流程模块

责任链模式对用户进行通用的判断

规则树模型对奖品进行定制化判断

执行抽奖算法得到奖品ID，生成奖品订单



### 发放奖品模块

情景：奖品库存扣除 + 用户表次数添加 作为一个一致性。

问题：在高并发场景下容易引发资源竞争问题。

目标：化解并发风险，实现业务解耦，同时保障两份数据的一致性

行动：

- 奖品库存扣除 + 用户表次数添加 作为一个一致性。
- 生成奖品库存流水 + 用户表次数添加 作为一致性
- 生成奖品订单，定时任务轮询事件，完成异步解耦。



### 返利模块

- 签到：生成行为返利订单 → 创建积分订单 + 充值订单 → 消费积分订单、充值订单 + 添加账户积分、抽奖次数
- 购买：生成充值订单 + 扣减积分 → 消费充值订单 + 添加账户抽奖次数





### 限流

1. 定义注解类(用户名，每秒请求次数，多少次后加入黑名单，降级方法)
2. 定义AOP切面类，保证Spring的bean会经过
3. 定义切面方法，保证对什么方法进行前置处理(比如标注这个注解，就会进入)。
4. 如果拦截到，获取 注解类属性信息 和 参数列表(ProceedingJoinPoint)
5. 黑名单拦截：当还在限流的时候，用户访问超过十次。
6. 限流拦截：获得不到令牌，则限流，并且黑名单次数加1。





### 降级

1. 标识限流注解类，属性为字符串“degradeSwitch:close”。
2. 通过config配置类的进行初始化zookeeper的Factory工厂。
3. Factory构造器对zookeeper节点初始化，并添加监听器监听变化。
4. Factory实现Bean初始化之后接口，SpringBean初始化完成后，存入缓存。





### 责任链抽奖

1. 公共抽象类有 接口属性，和可以返回这个属性的方法。
2. 通过工厂类根据规则进行拼接。
3. 比如：通过构造器返回实现类集合，然后根据配置类进行顺序拼接，最后提供可以返回的根节点。





### 规则树过滤

1. 存在MySQL
2. 启动时，通过一个请求进行预热到redis
3. 使用时，是一个类，包含 属性Map，key是条件，value是下个节点。





### 抽奖算法

比如：

- 总概率是100%，这个奖品的概率是30%，生成30个奖品。别的奖品概率是40%，则生成40个奖品。最后打乱奖品排序
- 最后总的奖品数量，取随机值。





### 监听器

- 消费用户奖品订单，更新账户奖品次数。
- 消费充值订单，更新账户抽奖次数。
- 消费行为返利订单，创建积分订单 + 充值订单。





### 登录的token生成

- 签名算法 → 证件类型
- 用户ID → 身份证号
- 加密签名 → 公安局盖章

原始签名(isjhd) -> 编码签名(Base64 编码，统一字符编码) -> 加密签名(HS256 对称加密算法，生成 JWT 签名

token = 存放内容 + 唯一标识(随机数) + 生成时间 + 用户ID + 编码签名和加密算法





## 扩展点

### 订单定时任务架构性能优化

情景：不同功能对应独立订单表，每张表单独配一个定时任务轮询处理

问题：

- 冷门功能会出现大量空轮询，资源浪费严重
- 而且功能扩容只能生硬新增定时任务。

行动：

- 先新增一张统一任务表，所有活动生成订单时同步写入该表
- 后续进一步升级架构，改用「定时任务推送消息 + MQ 路由分发到各自监听器 + 监听器消费处理」的模式

结果：现在新增活动不用再无脑加定时任务，架构弹性和整体性能都得到了提升。





### 防超卖

情景：Redis 做热点库存缓存，承接海量并发请求，缓解 MySQL 的读写压力

问题：

- Redis 与 MySQL 的库存数据最终一致性
- 服务节点意外崩溃时，如何保证数据不丢失、不错乱
- 网络 故障时，如何避免超卖（核心风险）、少卖问题。

行动：

- 服务崩溃
  - 立即降级，后续通过核实mysql订单表成功量进行恢复。
- 网络出现问题
  - redis出现少量网络抖动，会出现少买问题，不用在意。
  - mysql出现少量网络抖动，会出现超卖问题
    - 理想情况：MySQL 写入失败，立即回滚 Redis 的预扣减库存，恢复缓存数据。
    - 现实情况：故障期间不强制回滚，标记异常订单，后续通过人工修复库存。





### 订单表爆炸问题

情景：我们的订单表属于典型的流水型表，业务持续运转会不断新增数据，表容量会随时间持续膨胀。

问题：系统内有多处定时任务需要定期检索、更新订单数据

行动：采用**索引优化 + 分批查询**的组合方案。

- 索引优化：创建时间 + 订单状态 建立联合索引
-  分批查询：limit 分页



## 优化余地

1. 使用分库分表
2. 可以使用es专门为后台人员提供查询数据
3. 抽奖算法可以再优化一下

## 面试问题



### 订单库数据量特别大，定时扫描效率极低，怎么解决？

1. 索引 + 冷热数据分离：订单状态 + 时间 建立索引。
2. 分批扫描，禁止全量拉取： 每次只处理 100~500 条，循环执行。
3. 架构优化：告别定时扫描，从「轮询」变「事件触发」。
4. 读写分离，分库分表。
   - 垂直拆分：垂直分库(按业务模块拆库)；垂直分表(按字段冷热拆表)。
   - 水平拆分：水平分表(同库多表)；水平分库(多库多表)。



### 什么情况会导致超卖？

1. 先查库存、后扣库存，非原子并发；
2. MySQL RR 快照读无行锁，事务隔离导致并行读取；
3. Redis 缓存库存不一致、更新延迟；
4. 集群环境本地锁失效，无分布式锁；
5. MQ 重复消费、异步无幂等；
6. 读写分离主从延迟读脏数据；
7. 库存更新 SQL 无库存大于 0 的判断；
8. 接口无防重、恶意重复请求；
9. 事务异常，库存回补补偿缺失。





### 不能用时间、状态查订单表，用什么方式解决补偿问题？

1. 查是否有流水。
2. Redis 存临时占用，占用记录。



### 分布式系统下最终一致性有哪些实现方案？

1. TCC 柔性事务：三段式手动补偿事务，资源冻结 + 确认提交 + 回滚释放，完全无锁、高性能。
2. SAGA 模式：针对多服务长流程（下单→支付→发货→物流→售后），正向串行执行每一步，一旦失败，反向执行每一步的补偿接口。
3. 定时对账 + 兜底补偿：定时任务，基于唯一业务 ID、流水台账，比对库存、订单、支付数据。发现差异；自动触发补偿（回补库存、关闭无效订单）。



### 千万级订单宽表分页查询优化方案

**第一优先级**：改`SELECT *`为指定字段 + 优化分页逻辑（当天见效）；

**第二优先级**：建**联合覆盖索引**（解决多条件全表扫描）；

**第三优先级**：垂直分表 + 冷热数据分离（根治宽表）；

**第四优先级**：分库分表 / ES（支撑未来数据增长）。
