# rpc

## 介绍

需求背景：满足微服务之间的通信

主要功能：服务注册，服务发现，负载均衡

技术架构：

- Netty Reactor 主从多线程模型，基于NIO同步非阻塞通信。
- Spring保障服务初始化
- Netty负责实现通信框架
- Zookeeper负责对外暴露服务

有什么功能：服务注册模块、远程传输模块、服务发现模块、动态代理模块、负载均衡模块、解压缩模块、序列化模块、关闭钩子模块。



## 实现功能(初始化阶段)

### 初始化流程

标注的服务类如何注册到spring

>
> 服务端为什么不直接加入spring?
> 主要是了解SpringBoot如何启动，写了个类似的

4. 完成指定类注册到spring

最后只需要在指定类上标记，@RpcService(group = "test1", version = "version1")



### 请求发送流程

1. 客户端动态代理
2. 服务发现节点
3. 负载均衡选节点
4. 发送请求 -> 编码 -> 压缩 -> 序列化
5. 计算机网络 运输层 -> 网络层 -> 网链层 -> 硬件层
6. 操作系统(为什么能找到线程 )：网关接收数据 -> 写入socket缓存区(DMA拷贝)
7. 操作系统唤醒线程 -> selector被唤醒(处理IO事件 通过channel传输数据 -> ByteBuf 存储数据) -> 反序列化、解压、解码 -> 处理业务

> request内容
>
> 魔数(4字节)、版本(1字节)、消息长度(4字节)、消息类型(1字节)、压缩类型(1字节)、序列化类型(1字节)、请求ID(4字节)、body



### 初始化Netty服务端

1. 注册自定义关闭钩子
2. 注册三个分组线程池，建立连接组、读写组、业务组

4. 新建服务端channel
5. 设置参数，禁止攒包、建立连接的队列长度
6. 流水线，空闲检测 -> 粘包/拆包 -> 编解码 -> 设置业务处理器、线程组



### 初始化Netty客户端

1. 设置一个线程组
2. 新建客户端channel
3. 设置连接超时时间
4. 流水线，心跳发送 -> 粘包/拆包 -> 编解码 -> 设置业务处理器



### 服务发布到zookeeper

- 先判断是否是这个注解

- zookeeper上创建节点



### 字段注入动态代理对象

基于JDK动态代理，实现了一个接口的自定义代理类

- 判断这个属性是否标注了相关注解

## 实现功能

### 远程传输

- 新建CompletableFuture
- 调用服务发现模块，发现地址
- 通过地址获取对应映射的channel
- CompletableFuture 和 请求ID建立映射
- 封装RPC消息，调用channel发送请求方法
- 阻塞等待CompletableFuture响应

其他线程，收到响应后，调用CompletableFuture.complete(响应)，即可唤醒



### 解压缩

使用gzip压缩

1. 不生成文件，只压缩字节
2. Java原生支持
3. 压缩比高 并且 速度快
4. 跨语言、跨平台都能解析。



### 序列化

使用kryo进行序列化

- 速度最快、序列化体积最小
- 不支持跨语言
- 适合：Java 内部 RPC 调用、Redis 缓存 Java 对象、本地高性能数据传输



### 编解码

编码

- 新建ByteBuf
- 设置魔数、版本、消息长度(占位)、消息类型、序列化类型、压缩类型、请求ID
- 序列化、压缩Body
- 设置Body
- 设置消息长度(请求总长度)
- 添加到list，解决双向编解码问题



解码

- 构建RPC消息
- 设置消息类型、序列化类型、压缩类型、请求ID
- 消息长度 - 请求头长度 = body
- 解压
- 反序列化(区分请求和响应)
- 添加到list，解决双向编解码问题

## 亮点

### Spring集成

情境：

- 为了实现项目启动时自动加载
- 对实现 服务端服务自动注册 和客户端属性动态代理。
- 同时整合 ZooKeeper 作为注册中心，完成服务的注册与发现。

任务：接入 Spring Bean 生命周期，拆分为**Bean 初始化前置**（服务端注册）和**Bean 初始化后置**（客户端注入）

行动：

- 扫描器扫描类注册springbean
- springbean生命周期中，识别注解类，解析注解配置，提取服务分组、版本号
- 服务端则注册到本地和zookeeper，客户端则创建代理对象



### 负载均衡

任务：实现一致性哈希负载均衡器。解决节点动态变化时的请求倾斜问题。

行动：

- 使用`TreeMap<Long, String>`作为哈希环存储，实现**O(logN)** 时间复杂度的节点查找
- 为每个真实服务节点创建**160 个虚拟节点**
- MD5生成16 字节数组，保证哈希值分布均匀
- 一个IP生成40个16个字节数组，1个字节数组生成虚拟节点
- 将 4 字节数据转换为**32 位无符号 Long 类型**，作为哈希环的 key
- 对调用的**服务唯一ID**进行 MD5 加密并计算哈希值
- 在 TreeMap 中查找**第一个大于等于该哈希值**的虚拟节点



### 单例 Bean 全局唯一性

背景

- ConcurrentHashMap 缓存单例，仅保证单个 get/put 方法线程安全，会导致重复创建的问题。
- HashTable 缓存单例，锁的范围太广了，而且存在无意义获取锁的情况。

目标：在这两者之间寻求权衡

行动：

- 双重检查锁 \+ HashMap + Holder 可见性包装类
- 先获取，没有则加锁，再获取，再创建对象

结果：读不加锁，写加全局锁，并且不会重复创建对象。



### SPI

目标：实现使用时再加载，通过配置文件决定加载哪个类

行动

- 一个接口绑定一个加载器，加载器包含接口类型，实例对象，类对象



## 扩展点

### SPI全局唯一性，锁粒度优化

背景：写锁是全局锁

目标：将写锁优化成节点锁

行动：ConcurrentHashMap 有个方法，有则获取，无则创建，先创建空的包装类，然后再锁包装类







## 性能优化

- 池化请求对象、池化ByteBuf
- 建立连接请求一个线程池、读写请求一个线程池、业务请求一个线程池



- 使用 JDK 原生序列化：速度慢、体积大、频繁创建对象
- 粘包拆包处理不当：大报文下重复解析、内存拷贝
- 无状态编解码：每次编解码新建对象，GC 压力大



- TCP_NODELAY未开启：Nagle 算法导致数据包延迟发送
- SO_BACKLOG过小：服务端连接队列满，新连接被拒绝
- 发送 / 接收缓冲区（SO_SNDBUF/SO_RCVBUF）过小





## 面试问题

### 为什么使用gzip？

1. 不生成文件，只压缩字节
2. Java原生支持
3. 压缩比高 并且 速度快
4. 跨语言、跨平台都能解析。

什么不用 Snappy/Protobuf 压缩，偏偏选 Gzip

- Snappy：压缩率太低，只适合低延迟的场景，且需要引入第三方依赖
- Protobuf ：和序列化模块强耦合，Gzip 可以和任意序列化器（Kryo/Hessian）搭配。



### 为什么不使用 Java 原生序列化？

1. 速度慢、体积大
2. 无法跨语言
3. 严重的安全漏洞：反序列化攻击



### Kryo、Hessian、Protostuff 各自的优点和缺点

1. Kryo
   - 速度最快、序列化体积最小
   - 不支持跨语言
   - 适合：Java 内部 RPC 调用、Redis 缓存 Java 对象、本地高性能数据传输
2. Hessian
   - 跨语言支持
   - 性能略逊于 Kryo
   - 适合：跨语言服务通信、传统分布式系统、稳定。
3. Protostuff
   - 跨语言、体积极小、性能顶尖
   - 结构化数据，适合持久化存储
   - 适合：微服务跨语言通信、数据持久化、极致紧凑。



### 如何解决粘包/拆包

1. 给消息加一个「长度字段」

2. 解码器设置参数
   - 长度偏移量，长度的长度，body的偏移量
3. 读取这个字段，精准识别完整消息的边界，自动拆分粘包、组装拆包。





### Netty 传输模块的核心瓶颈

1. 内存与 GC 瓶颈：未池化的请求对象 / ByteBuf 
2. 线程模型阻塞瓶颈：采用主从 Reactor 线程模型，一旦 IO 线程阻塞，传输直接瘫痪
3. 编解码 / 协议低效瓶颈：
   - 使用 JDK 原生序列化：速度慢、体积大、频繁创建对象
   - 粘包拆包处理不当：大报文下重复解析、内存拷贝
   - 无状态编解码：每次编解码新建对象，GC 压力大
4. TCP 底层网络参数瓶颈：
   - TCP_NODELAY未开启：Nagle 算法导致数据包延迟发送
   - SO_BACKLOG过小：服务端连接队列满，新连接被拒绝
   - 发送 / 接收缓冲区（SO_SNDBUF/SO_RCVBUF）过小
