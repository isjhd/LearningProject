# AIAgent

> 项目使用 Spring AI + Google ADK + Tauri（+Typescript），结合运行时智能体设计，涵盖；`Agent WorkFlow`、`上下文管理（对话追踪、搜索、提示词）`、`意图识别（+LLM）`、`混合窗口裁剪`、`动态提示词（ Prompt 组装器、里程碑追踪）`等，核心设计，构建一整套 AI Agent 智能体服务工具。
>
> 可以为项目工程，扩展添加 mcp、skills 技能等，为你的服务器做智能化运维服务管理。如；`日志分析`、`系统健康度巡检`、`内存泄漏排查`、`复杂项目链路耗时处理`、`项目压测优化建议等等场景`。
>
> AI Agent 要解决的就是一整条研发交付路径服务，包括；研发设计（spec规约）、工程编码（WaLiCode）、项目上线/运维（WaLiSSH）等





## 介绍

**需求背景**：针对传统研发交付流程中部署排障效率低、人工操作误差大的痛点，设计并实现 AI Agent 。通过可扩展的技能插件，支撑服务器智能化运维、项目自动化部署排障等场景。

主要功能：AIAgent远程操作服务器

技术架构：Spring AI，Google ADK，SpringBoot，MySql，jdk17

主要工作：AIAgent装配层开发，AIAgent编排层开发、AIAgent上下文构建(两个)、prompt拼接、对接服务端shell、SSH 命令执行工具开发、类图和时序图的编写。

## 扩展点

### JSch对接命令行窗口

**背景**：当时业务需要程序去操作 Linux 命令行，我选用 JSch 实现 SSH 交互，封装了 read 读取控制台返回、write 发送命令

**问题**：Shell 通道 IO 流不是线程安全

**行动**：用单例模式，对读写方法加锁保证互斥访问，以此保障并发安全。





## BUG解决

### JSch 通道内存泄漏问题

问题：JSch 执行远程 Shell，每次都是新建 ChannelShell 通道，而不是复用。

行动：我以 sessionId 作为会话标识，定义四个线程安全 Map。统一托管 Shell 通道、输入输出流、输出缓冲区。



### 验证码重复收取

**问题**：实习生再debug代码时，发现会重复生成验证码。

**行动**：

- 先debug，再画图，画完图后发现类似八股文，好像是单例模式
- 后面我使用双重检查锁：先获取实例，然后加锁，然后获取，然后创建。发现就没这个问题了





### 线程之间传递上下文

场景：调用 AI 大模型时，因为是耗时的，为了不阻塞业务主线程，放到异步线程执行，会话 ID 绑定到ThreadLocal。

问题：AI执行 tools工具 / skills 后，可能会创建新线程，拿不到父线程的会话ID。

行动：选用InheritableThreadLocal，父线程创建子线程时会自动把上下文拷贝过去。

局限：

- 只有新建线程才会拷贝，如果用线程池复用旧线程，它不会自动复制，线程池场景不能直接用，需要手动透传上下文做兼容。
- 如果是创建新线程，而不是创建子线程，也拿不到数据，选用另一个阿里的ThreadLocal对象即可。





## 面试问题

用docker compose不行吗

Docker Compose 解决「环境一致性 + 部署标准化」，AI Agent 解决「流程编排 + 数据迁移 + 故障自愈 + 全链路自动化」



我编写一个skills.md 和你这样写一个 Java工具包 skills 它的区别是什么

- 可扩展性差，Java利用设计模式规避。
- 上下文管理难，难以实现数据共享。
- 可能存在内存泄漏问题。java的优点在于JVM的内存管理。



为什么用Java不用python

- Python 非常适合做 Agent 原型、快速验证想法、调试大模型调用，开发速度快生态丰富。
- 但如果要做**生产级、高并发、微服务化的 AI Agent 系统**，Java 会更有优势。



为什么使用jsch作为连接ssh的包

- 有更好的选择，但是，团队很多老业务大量使用 JSch，大家对它的坑非常熟悉，连接泄漏、流读取阻塞、编码、超时处理都有现成封装好的工具类、工具模板。
- 如果选用更好的选择，团队缺少实战踩坑经验，需要重新封装工具、重新压测验证，会增加项目迭代周期，引入新的未知风险。
- 而且有很多老机器，JSch 是兼容的。
- 而且我们是自己使用，不对外。



为什么用google adk

- 我们项目要做可商业化落地的 AI Agent，需要完整的 Agent 运行能力，还要对接 MCP 远程工具，同时前端要流式展示 Agent 思考和工具调用过程，综合对比后选择 Google ADK。
- 普通大模型 SDK 只是发请求拿返回，Agent 的循环逻辑、状态流转要自己写。ADK 把 Agent 运行时做了标准化封装，我不用从零实现 ReAct 循环。
- ADK 原生支持 **MCP**，降低工具接入成本。
- 不用自己解析大模型返回、切割 返回内容，区分哪些是思考，哪些是工具调用。
- 将自己写的工具封装成skills比较方便



Google ADK：LlmAgent（Agent 基类）、BaseLlmFlow（ReAct 循环引擎）、FunctionTool（工具包装）、BasePlugin（插件基类）、InMemoryRunner（运行器）

| 类               | 职责           | 核心定位                                                     |
| ---------------- | -------------- | ------------------------------------------------------------ |
| `LlmAgent`       | Agent 基类     | 代表一个智能 Agent 实体，持有模型、工具、prompt、记忆，业务 Agent 继承它 |
| `BaseLlmFlow`    | ReAct 循环引擎 | **核心执行流**，实现思考→调用工具→观察→再思考的 ReAct 循环逻辑 |
| `FunctionTool`   | 工具包装       | 将普通 Python 函数包装成 Agent 可调用的工具，自动生成 Function‑call schema |
| `BasePlugin`     | 插件基类       | 扩展能力，可注入工具、prompt、生命周期钩子，解耦业务能力     |
| `InMemoryRunner` | 运行器         | 内存内执行 Agent 会话，维护线程上下文、消息历史，本地调试首选 |



Spring AI：ChatModel（模型调用）、OpenAiChatModel（OpenAI 实现）、ToolCallback（工具回调接口）、Prompt（提示词对象）

| 类 / 接口         | 职责               | 定位                                                         |
| ----------------- | ------------------ | ------------------------------------------------------------ |
| `ChatModel`       | 大模型聊天顶层接口 | **统一模型调用入口**，屏蔽不同大模型厂商差异                 |
| `OpenAiChatModel` | OpenAI 协议实现类  | `ChatModel` 的 OpenAI 兼容实现，对接 OpenAI / 智谱 / DeepSeek 等兼容接口 |
| `ToolCallback`    | 工具回调接口       | Agent 工具调用的抽象，模型返回 function‑call，框架回调该接口执行业务逻辑 |
| `Prompt`          | 提示词对象         | 封装完整请求上下文：系统提示、用户消息、历史消息、工具定义、参数 |





**RxJava：**`Flowable`**（响应式流）、**`concatMap`**（顺序转换）、**`defer`**（延迟创建）**

| API           | 职责                 | 核心定位                                                     |
| ------------- | -------------------- | ------------------------------------------------------------ |
| `Flowable<T>` | 响应式流（支持背压） | 发射 0~N 个数据，支持下游背压，IO / 网络场景首选。<br />它是**数据的生产者**，也就是那条水管。 |
| `concatMap`   | 顺序转换操作符       | 把每个元素映射成流，**严格按输入顺序串行执行**，前一个流结束才跑下一个。<br />这是**启动开关**。 |
| `defer`       | 延迟工厂包装         | **订阅时才创建源 Flowable**，不是声明期创建，解决变量捕获、重复执行问题。<br />它是**数据的消费者**，也就是接水的人。 |



**白名单怎么做的**

1. 服务器实例白名单：哪些服务器允许被连接，数据库维护服务器配置表。
2. 命令白名单：禁止让 Agent 执行任意 shell，有高危命名需要交由用户判断。
3. 应用层 IP 白名单：客户端 IP，校验是否在白名单。
4. 底层 Linux SSH 侧白名单：`/etc/ssh/sshd_config`配置`AllowUsers`，只允许我们工具使用的 ssh 账号登录；



**超时怎么做的**

使用 future.get(超时时间)

超时发送中断标记(工具类内，非底层)



**注入问题如何解决**

使用字符串拼接，命令 + 路径，命令由正则判断，路径交由底层的一个工具类判断。





**怎么测试**

1. 开发完功能，先写JUnit单元测试，做 mock 对象，本地跑通。
2. 本地开始跑，做接口测试。





**出了问题如何排查。**

1. 先看是哪个接口出问题了，报错码是多少
2. 然后看监控：CPU 飙高？内存泄露？GC 频繁？数据库打满？MQ 堆积？
3. 然后看日志，是哪个类出问题了。
4. 自己本地复现
5. 查资料，丢给AI。







**前后端怎么联调**

联调前期

1. 定接口文档
2. 约定规范
3. mock 数据
4. 对齐入参出参

本地联调

1. 后端自测：postman 单独调用自己接口

测试环境联调

1. 代码提交，部署到测试环境
2. 前后端：前端连测试环境后端域名，完整走业务流程，跑通正向、反向用例；
3. 联调覆盖场景：正常流程，参数为空、非法参数，业务异常，边界值。

问题排查手段

- 看请求日志：请求参数、响应结果是否符合预期；
- 网关日志、Feign 调用日志，看服务之间请求有没有发出去；
- 抓包：Fiddler、浏览器 Network，确认请求体、响应体；
- 如果是微服务：看链路追踪 SkyWalking，看哪一层报错；
- 核对文档：很多联调 bug 就是**文档和代码不一致**。

联调收尾

1. 所有业务流程跑通；
2. bug 修复回归；
3. 补充完善接口文档；
4. 回归测试，准备上预发、生产。
